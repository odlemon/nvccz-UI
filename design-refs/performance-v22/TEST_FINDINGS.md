## FINDING-PM22-001

**Title:** `performance-v22`'s module config still declared `/performance-v22/*` paths after the real rename to `/performance`, causing `getModuleByPath` to silently resolve every `/performance` page to the wrong, superseded module
**Module:** Performance (frontend `nvccz-new`, cross-cutting `lib/config/modules.ts`) · **Dimension:** UAT · **Category:** Module-config staleness (same bug class as an already-fixed Portfolio finding)
**Severity:** MEDIUM — no data loss and the page itself renders correctly, but the client-side "which module is this" state is wrong on every load, with downstream effects on the module switcher and any client-side permission/feature check keyed by module id
**Persona affected:** Every staff user on any `/performance/*` page
**Surface:** `lib/config/modules.ts` (`performance-v22` entry); `components/layout/client-design-module-shell.tsx`

### Investigation (live on dev, 19 September 2026)

Navigating to `https://dev.matanho.com/performance-v22` redirects to `/performance`, which renders the
real V22 Command Centre with live, backend-driven data (confirmed: filters, real "not yet tracked"
empty states, not canned mock fixtures) — matching `middleware.ts`'s own comment, `// Performance
Management (Matanho V22 — canonical /performance)`. So `/performance` is the correct, current,
intentional URL for the V22 experience — the same short-URL-promotion pattern already used for
Procurement (`/procurement` now V23) and Portfolio (`/portfolio` now V11).

However, `lib/config/modules.ts`'s `performance-v22` entry still declared `path: "/performance-v22"`
and every subModule under `/performance-v22/*` — never updated to match the real rename. Traced the
live impact:

- `getModuleByPath(path)` (`lib/config/modules.ts`) filters `MODULE_CONFIG` for any module whose `path`
  or subModule paths match, then — per its own doc comment, which *already* describes exactly this
  Performance scenario by name — prefers the non-superseded match when more than one module claims the
  same path. But `performance-v22`'s config never actually claimed `/performance` at all, so there was
  no ambiguity for that tie-break to resolve: `getModuleByPath('/performance')` matched *only*
  `performance-management` (the old module, `hiddenFromSwitcher: true` and listed in
  `SUPERSEDED_MODULE_IDS`), because its own subModules still declare `path: "/performance"` etc. from
  before it was superseded.
- `ClientDesignModuleShell` (used to host `/performance`'s content) initializes `currentModule` from a
  `defaultModuleId` prop (presumably `"performance-v22"`), then a `useEffect` immediately calls
  `getModuleByPath(pathname)` and overwrites `currentModule` with whatever it returns — confirmed by
  reading the component: `const module = getModuleByPath(pathname); if (module) setCurrentModule(module.id)`.
  For `/performance`, this silently flips `currentModule` from `"performance-v22"` to
  `"performance-management"` on every single page load.
- This same collision also meant `getModuleByPath('/performance/strategy')`,
  `getModuleByPath('/performance/scorecards')`, etc. returned `undefined` entirely for most pm22
  subroutes (the old module's own subModule paths are different — `/performance/configuration/strategy`,
  not `/performance/strategy` — so *neither* module actually matched), an even more direct resolution
  failure than the dashboard case.

### Assessment of blast radius before fixing

Checked whether `performance-v22-layout.tsx` (the real, vendored layout `/performance` actually uses)
reads `MODULE_CONFIG`/subModule paths for its own sidebar or navigation at all — it does not; the
vendored runtime has its own internal nav table (`PM22_NAV_PAGES`, generated by the extract script), so
changing these path strings could not break real in-app navigation. Checked how `module.path` is
consumed elsewhere: only by the module-switcher tile's click handler
(`window.location.href = module.path` in `app-switcher.tsx` / `arcus-app-switcher-dropdown.tsx`) — fixing
the path to `/performance` makes that tile navigate directly there instead of via the
`/performance-v22` redirect hop, a strict improvement, not a regression. Confirmed server-side route
permissioning is unaffected: `middleware.ts` has its own separate, already-correct route table mapping
literal `/performance/*` paths straight to `{module: 'performance-v22', subModule: 'pm22-*'}`, with its
own `performance-v22 → performance-management` alias specifically for `ROLE_PERMISSIONS_MAP` lookups —
none of that reads `lib/config/modules.ts` at all, so this fix only touches client-side module-identity
state, never access control.

### Fix

`lib/config/modules.ts` — `performance-v22`'s `path` changed from `/performance-v22` to `/performance`;
all 11 subModule paths changed from `/performance-v22/*` to `/performance/*`. Mirrors exactly how the
equivalent Portfolio finding was fixed (`portfolio-v11`'s config corrected from `/portfolio-v11` to
`/portfolio`).

Commit `6adfe61`, branch `feature/performance-v22-live`.
